# memory_eval_v1 测评集

这个测评集用于快速验证 CodePulse 长期记忆沉淀链路是否“可用、有价值、不会乱记”。

## 数据来源

- 主要来源：同事真实 CP SQLite 数据库 `D:\opencode-dev\opencode-dev.db`
- 隔离索引库：`D:\codepulse\Codepulse-Memory-Lab\data\eval\memory_eval_index.db`
- 回填范围：7 个真实主会话，85 条用户事件
- 本版固化样本：40 条单 turn + 7 组连续场景

## 为什么不是同一个会话

测评集不强行归为同一个会话。长期记忆要验证的是跨项目、跨会话是否能稳定抽取、过滤、合并和更新，所以 v1 采用“跨真实会话抽样”的方式。

每条 case 都保留原始 `source_db`、`session_id`、`turn_id`，后续脚本可以回到原始 CP SQLite 和隔离 lab SQLite 读取证据。

## 测什么

单 turn 基础集主要测：

- 需求参数是否被正确过滤
- 用户协作偏好是否能沉淀
- 编译/烧录失败是否能沉淀为工程经验
- 运行现象是否能沉淀为“现象 → 原因 → 解决 → 验证”
- 无意义输入是否 noop
- 工具/平台限制、当前项目配置等边界内容是否误沉淀

单 turn 隔离评测只判断“这一轮本身是否值得写入长期记忆”。因为每条 case 都使用独立用户记忆空间，所以它不能把 `update_memory` / `merge_memory` 作为唯一正确动作；需要已有记忆参与的合并、更新、补验证能力，放到连续场景集中评估。

连续场景集主要测：

- 多轮问题修复是否合并成一条高质量经验
- 相似用户偏好是否 update/merge，而不是重复 create
- 用户确认修复成功后，记忆是否补上“已验证”
- 主题摘要是否随记忆变化而更新

连续场景集才用于验证“先创建、后更新/合并、再补验证状态”的完整链路。

## 通过标准（第一版）

- 需求参数类：80% 以上应为 noop 或只保留为证据，不进入长期记忆
- 用户偏好类：80% 以上能沉淀出可复用协作习惯
- 编译/烧录失败类：70% 以上包含“现象/原因/修复/验证”中至少 3 项
- 运行现象类：70% 以上能形成可复用工程经验
- 重复/连续场景：至少出现 update 或 merge，不能全部 create
- 无意义输入：90% 以上 noop
- 每条写入 memory 都能回溯到原始 turn / evidence

详细判定边界见：[长期记忆评测集重审标准](../../docs/长期记忆评测集重审标准.md)。

## 文件说明

- `cases.jsonl`：单 turn 样本，每行一个 JSON 对象。
- `scenarios.json`：多 turn 连续场景。
- `sources.md`：数据来源和已回填会话说明。
