# 长期记忆评测指标设计

本文档定义 CodePulse Memory Lab 的长期记忆评测标准。目标不是只看“最后生成了什么记忆”，而是同时评估：

1. 过程是否可信：模型是否拿到了该拿的信息、是否查了已有记忆、动作选择是否合理。
2. 结果是否有用：沉淀出来的记忆是否能长期复用、是否被证据支撑、范围是否合适。

第一轮完整评测结果保留为 baseline：

```text
reports/eval-baselines/baseline-20260922-first-full-run
```

后续优化后，应使用同一套评测指标重新评审 baseline 与新 run，形成可对比结果。

---

## 一、评测集需要包含的字段

每个评测 case 建议包含以下信息。

| 字段 | 含义 | 用途 |
|---|---|---|
| `scenario_id` | 场景 ID | 用于多轮 turn 连续评测 |
| `turn_id` | 当前 turn ID | 关联原始对话、证据包、ReAct 日志 |
| `case_type` | 记忆类型，如用户偏好、编译失败、运行现象定位 | 决定使用哪套质量标准 |
| `expected_evidence` | 本 turn 必须进入证据包的关键信息 | 评估证据覆盖率 |
| `expected_action` | 期望主动作，如 create、merge、noop、update_topic | 评估动作是否合理 |
| `allowed_actions` | 允许出现的动作集合 | 避免过度限制模型路径 |
| `forbidden_actions` | 禁止动作集合 | 防止明显错误操作 |
| `should_extract` | 应沉淀的信息点 | 评估是否漏掉关键记忆 |
| `should_not_extract` | 不应沉淀的信息点 | 评估是否混入一次性细节 |
| `expected_process` | 过程要求，如需要加载已有记忆 | 评估过程是否可信 |
| `quality_target` | 目标质量等级 | 用于人工/模型评审参考 |

注意：不建议写死“必须调用某个工具几次”。更合理的是要求“必须完成某类过程”，例如“同类补充场景必须查看已有记忆”，而不是固定具体调用路径。

---

## 二、过程指标

过程指标用于判断“模型整理记忆的链路是否可靠”。核心只保留 4 个，不把已经做过的幂等、失败恢复、并发等工程稳定性指标混进来。

### 1. 关键证据覆盖率

意义：

判断本轮 turn 中关键 user / assistant / tool / 验证信息是否进入了证据包。防止模型没有看到关键证据就下结论。

数据来源：

- `react-logs/*.json` 中的 core / candidate / pointer
- `eval-detail.json`
- 必要时通过 pointer 回查原始 CP SQLite

可脚本计算部分：

```text
证据关键词命中率 = 命中的 expected_evidence 关键词数 / expected_evidence 关键词总数
```

适合硬规则检查：

- 用户反馈的现象是否出现
- 助手定位出的根因是否出现
- 修复方案是否出现
- 编译/烧录/用户确认结果是否出现

需要大模型判断部分：

- 证据语义是否真的完整，而不是只命中了关键词
- 证据之间是否能组成“现象 → 根因 → 修复 → 验证”的链路
- pointer 是否足以回查缺失细节

### 2. 已有记忆检查合理性

意义：

判断模型在做新增/合并/更新前，是否看过已有 memory/topic，避免重复创建和错误合并。

数据来源：

- ReAct 步骤中的 `load_memory_index`
- 工具调用日志
- 最终动作 `create_memory` / `merge_memory` / `update_topic` / `noop`

可脚本计算部分：

```text
记忆索引加载率 = 有 load_memory_index 的 turn 数 / 需要检查已有记忆的 turn 数
```

```text
重复 stable_key 数 = 同一次 run 内重复 stable_key 的数量
```

```text
后续 turn 合并率 = 多轮场景中 merge/update 动作数 / 后续有效动作数
```

需要大模型判断部分：

- 加载到的已有记忆是否真的相关
- 本该合并的内容是否误新增
- 本该新建的独立经验是否误合并
- 主题是否需要扩大、拆分或改名

### 3. 动作选择合理性

意义：

判断模型最终选择 create、merge、noop、update_topic 是否符合本轮证据。

数据来源：

- `eval-detail.json` 中每个 turn 的实际动作
- 评测集中的 `expected_action` / `allowed_actions` / `forbidden_actions`
- ReAct 最终判断原因

可脚本计算部分：

```text
动作命中率 = 实际动作在 allowed_actions 内的 turn 数 / 总 turn 数
```

```text
禁止动作违规率 = 出现 forbidden_actions 的 turn 数 / 总 turn 数
```

```text
noop 命中率 = 低价值 turn 中实际 noop 的数量 / 期望 noop 的 turn 数
```

```text
单 turn 新增过多数 = create_memory 数量超过阈值的 turn 数
```

需要大模型判断部分：

- 开放场景里是否真的应该 noop
- 一轮新增多条是否是合理拆分，还是过度拆分
- merge 后是否丢失了关键差异
- update_topic 是否真的必要

### 4. 决策可解释性

意义：

判断模型是否清楚说明“为什么沉淀/不沉淀，为什么新增/合并/更新，为什么不是需求文档内容”。

数据来源：

- ReAct 日志中的 final reason
- `generated-memories.md` 中每条变化的原因

可脚本计算部分：

可做弱规则检查：

```text
理由存在率 = 有非空 reason 的动作数 / 总动作数
```

```text
理由关键词覆盖 = reason 中是否包含沉淀原因、动作原因、排除原因等关键词
```

需要大模型判断部分：

- 理由是否真正解释了动作
- 理由是否和证据一致
- 理由是否能让人复查
- 是否存在“看起来有理由，但其实泛泛而谈”

## 三、结果指标

结果指标用于判断“最终沉淀的记忆是否有价值”。

### 1. 长期复用价值

意义：

判断这条记忆未来是否能减少重复问答、减少错误定位、减少代码返工。

可脚本计算部分：

只能做弱检查，例如：

- 是否包含“适用场景”
- 是否包含“可复用原因”
- 是否不只是具体项目参数

需要大模型判断：

- 这条记忆是否真的可复用
- 是用户级、领域级、项目级，还是一次性任务信息
- 是否过于常识化，导致存了也没用

### 2. 证据支撑性

意义：

判断 memory 的每个关键结论是否能从证据中找到支撑。

可脚本计算部分：

```text
证据引用数 = memory 绑定的 evidence 数量
```

```text
关键字段命中率 = memory 中的现象/根因/修复词是否能在证据包中找到关键词
```

需要大模型判断：

- 证据是否真的支持该结论
- 是否把未验证猜测写成已验证经验
- 是否把助手推测误当成用户确认

### 3. 范围清晰度

意义：

判断记忆什么时候适用、什么时候不适用，避免太宽或太窄。

可脚本计算部分：

弱规则：

- 是否包含适用场景
- 是否包含触发条件
- 是否包含限制条件或注意事项

需要大模型判断：

- 范围是否刚好
- 是否把项目细节泛化成通用规则
- 是否把通用经验写得太窄，只能用于当前项目

### 4. 结构完整性

意义：

不同类型记忆应满足不同结构，不能用一套“现象/根因/解决/验证”检查所有记忆。

类型标准：

| 类型 | 必须关注的字段 |
|---|---|
| 用户协作偏好 | 适用场景、用户偏好、协作要求、价值 |
| 编译失败经验 | 错误现象、触发条件、根因、修复、编译验证 |
| 运行现象定位 | 现象、触发条件、根因、解决方案、用户/烧录验证 |
| 工程流程经验 | 触发场景、推荐流程、避免的问题、边界 |
| 硬件/外设经验 | 硬件条件、寄存器/接口约束、错误表现、验证方式 |

可脚本计算部分：

```text
类型字段覆盖率 = 已包含的必需字段数 / 该类型必需字段总数
```

需要大模型判断：

- 字段内容是否真实有意义
- 是否只是形式上写了“根因/验证”，但内容空泛

### 5. 项目噪声控制

意义：

判断是否把当前项目的一次性参数、路径、IO 表、临时需求混入长期记忆主体。

可脚本计算部分：

```text
禁止关键词泄漏率 = should_not_extract 中命中的项目细节数 / should_not_extract 总数
```

可检测内容：

- 具体路径
- 具体项目代号
- 具体 IO 映射
- 具体阈值
- 临时测试参数

需要大模型判断：

- 某个项目细节是否只是作为证据存在，还是污染了长期规则
- 某些具体例子是否有必要保留为“示例”

### 6. 合并/拆分质量

意义：

判断记忆颗粒度是否合适：不能所有东西都新建，也不能把不同根因硬塞进一条记忆。

可脚本计算部分：

```text
重复 stable_key 数
```

```text
单场景 create/merge 比例
```

```text
单 turn create_memory 数量
```

需要大模型判断：

- 语义重复但 stable_key 不同的记忆是否应合并
- 同一主题下的不同根因是否应拆成多条 memory
- 主题是否需要合并、拆分、改名

## 四、建议评分结构

建议总分 100 分，分为过程 40 分、结果 60 分。

### 过程分 40

| 指标 | 分值 | 主要来源 |
|---|---:|---|
| 关键证据覆盖 | 12 | 脚本 + 大模型 |
| 已有记忆检查合理性 | 8 | 脚本 + 大模型 |
| 动作选择合理性 | 12 | 脚本 + 大模型 |
| 决策可解释性 | 8 | 脚本 + 大模型 |

### 结果分 60

| 指标 | 分值 | 主要来源 |
|---|---:|---|
| 长期复用价值 | 15 | 大模型 |
| 证据支撑性 | 12 | 脚本 + 大模型 |
| 范围清晰度 | 12 | 大模型 |
| 类型结构完整性 | 8 | 脚本 + 大模型 |
| 项目噪声控制 | 8 | 脚本 + 大模型 |
| 合并/拆分质量 | 5 | 脚本 + 大模型 |

分数解释：

| 分数 | 结论 |
|---:|---|
| 90-100 | 高质量，可直接保留 |
| 80-89 | 可用，少量优化 |
| 70-79 | 勉强可用，需要优化 |
| 60-69 | 风险较高，应重写或人工复核 |
| <60 | 不建议进入长期记忆 |

## 五、哪些指标优先自动化

第一阶段优先做脚本可算指标：

1. 处理成功率
2. 动作命中率
3. 禁止动作违规率
4. 证据关键词命中率
5. 禁止信息泄漏率
6. 重复 stable_key 数
7. 单 turn 新增过多数
8. noop 命中率
9. 类型字段覆盖率

这些指标可以先用于稳定回归，不依赖外部模型。

第二阶段再加大模型评审：

1. 长期复用价值
2. 证据语义支撑性
3. 范围是否合适
4. 是否过度拆分或应该合并
5. 是否漏掉应沉淀信息
6. 主题摘要是否准确
7. 决策理由是否可信

当前阶段可以先由 Codex/人工评审承担大模型评审角色，后续再接入独立 judge 模型。

## 六、优化前后如何对比

每次优化后都生成一份新 run，然后和 baseline 对比。

对比项：

| 对比项 | 目标 |
|---|---|
| 处理成功率 | 不下降 |
| 动作命中率 | 上升 |
| 禁止动作违规率 | 下降 |
| 证据关键词命中率 | 上升 |
| 项目噪声泄漏率 | 下降 |
| 重复/过度拆分 | 下降 |
| 大模型评审平均分 | 上升 |
| 低于 70 分的 case 数 | 下降 |

重要原则：

旧 baseline 原始结果不修改。
如果只是新增评审标准，不需要重跑 baseline 抽取；只需要用新评审器重新评 baseline。
如果证据包结构或日志字段发生变化，旧结果缺少必要过程信息，才需要重新跑一版 baseline。

## 七、当前第一轮暴露出的主要问题

基于第一轮 baseline 的旧规则报告，目前可确认的问题是：

1. 旧评测规则没有按记忆类型区分，导致用户偏好类记忆被“缺少现象/根因/验证”误伤。
2. 范围清晰度没有系统评分，难以判断记忆是太宽、太窄还是刚好。
3. 部分场景提示“长期复用价值表达不明显”，需要大模型语义评审确认是真问题还是规则误报。
4. 少量记忆疑似混入一次性项目细节，需要区分“作为证据保留”和“污染长期记忆主体”。
5. 单轮新增过多需要复核，判断是合理拆分多个独立故障，还是过度拆分。

因此下一步优先级应是：

1. 把评测集字段补齐为“过程期望 + 结果期望”。
2. 先实现脚本可算指标。
3. 再生成评审输入包，由 Codex/人工按本文档标准打分。
4. 最后根据问题分类优化提示词、证据包和工具调用策略。
