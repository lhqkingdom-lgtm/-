# Memory Lab 架构设计文档

本文从头到尾梳理当前 Memory Lab 的架构、数据流、关键设计选择，以及为什么这样设计。

## 1. 项目目标

Memory Lab 的目标是为 CodePulse / CP 对话建立长期记忆系统，让系统能从真实开发长流程中沉淀：

1. 用户交互习惯；
2. 编译失败/成功经验；
3. 用户反馈现象后定位出的原因、解决方法和验证结果。

一句话目标：

```text
需求文档存“当前项目最终要做什么”；
长期记忆存“以后 CP 怎么少问、少错、少返工”。
```

## 2. 当前核心架构

当前链路：

```text
CP SQLite 原始会话
  ↓
turn 切分
  ↓
三层证据池 core / candidate / pointer
  ↓
PostgreSQL 入库
  ↓
ReAct 记忆维护 Agent
  ↓
读工具补证据
  ↓
memory-changes-v1 结构化计划
  ↓
本地校验 / 幂等 / 写库
  ↓
PostgreSQL 当前记忆表
  ↓
Markdown 导出审查
```

### 2.1 当前最新优化

当前已补充两项稳定性能力：

1. 长上下文批次选择增加 cycle 层软预算。单个大 turn 仍可处理，但多个大 turn 不会被一次性塞进模型，避免真实 CP 长会话导致 token 超限或判断不稳定。
2. `memory-changes-v1` 支持 `client_temp_id`。模型可以在同一个提交计划里先 `create_memory`，再用 `temp:xxx` 引用刚创建的 memory 建立关系，提交工具会自动替换为真实 `memory_id`。

这两项优化后，全量测试通过：

```text
339 tests OK
```

## 3. 为什么从 CP SQLite 开始

CP 当前真实会话数据存储在本机 SQLite 中，路径类似：

```text
C:\Users\<user>\.local\share\codepulse\opencode-dev.db
```

选择 SQLite 作为原始数据来源的原因：

1. 它是 CP 的真实运行数据，不是人工构造样例；
2. 能覆盖真实长流程，包括需求对齐、代码生成、编译修复、运行现象反馈；
3. 可回放，适合反复测试记忆系统；
4. 不需要先改 CP 主程序，就能验证记忆链路。

但 SQLite 不适合作为长期记忆主库：

- 原始会话结构不是为长期记忆设计；
- 不适合存用户主键、主题、冲突、证据池；
- 不适合做多轮维护和审查。

所以采用：

```text
SQLite 只作为原始证据来源；
PostgreSQL 作为 Memory Lab 的结构化工作库。
```

## 4. 为什么按 turn 切分

长期记忆抽取的基本单位不是单条 message，而是一轮任务 turn。

一轮 turn 中可能包含：

```text
user 反馈
assistant 诊断
tool 读文件 / 编译 / 修改代码
assistant 最终结论
用户确认
```

如果只看单条 message，容易丢失：

- 问题是否真的修复；
- 诊断是否只是猜测；
- 编译是否通过；
- 用户是否确认；
- 工具输出对应的是哪次修改。

所以当前以 turn 为单位处理：

```text
原始对话 → turn → 一轮证据包 → 一次记忆维护判断
```

## 5. 三层证据池设计

每个 turn 入库前会拆成三层：

### 5.1 core

核心证据，通常包括：

- 用户明确偏好；
- 用户明确反馈；
- 用户确认修复；
- 助手最终稳定结论。

作用：

```text
给模型最关键、最短的信息。
```

### 5.2 candidate

候选证据，通常包括：

- 工具结果摘要；
- 编译结果；
- 诊断过程摘要；
- 可能有长期价值但需要判断的信息。

作用：

```text
让模型看到更多上下文，但不强行认定为长期记忆。
```

### 5.3 pointer

原始指针，保存：

- 原始 message_id；
- part_id；
- source_type；
- 原始片段摘要；
- raw_pointer_id。

作用：

```text
当 core/candidate 不够时，让模型通过 expand_pointer 回查原始 CP 片段。
```

### 5.4 为什么不直接把全部原文给大模型

因为：

1. token 成本高；
2. 编译日志、工具输出很长；
3. 原文里有大量一次性过程信息；
4. 长期记忆只需要“可复用结论”，不是完整聊天记录；
5. 后续模型可通过 pointer 按需补证据。

因此采用：

```text
先给摘要和关键证据；
信息不足再回查 pointer。
```

存冲突处理过程。

用于记录：

```text

```

例如：

```text

```

## 7. 为什么用 PostgreSQL

选择 PostgreSQL 的原因：

1. 支持结构化表和 JSONB；
2. 适合存 topic/memory/conflict/evidence；
3. 方便 DBeaver 人工查看；
4. 后续可接入服务端；
5. 比 SQLite 更适合多用户、多任务、多索引场景。

MVP 中暂时没有做复杂版本链。

原因：

```text
先打通“沉淀链路”和“可解释更新”，版本链过早引入会增加维护成本。
```

当前用：

```text
current memory + metadata + conflict_records
```

来满足演示和 MVP 需求。

## 8. ReAct 记忆维护 Agent

当前 Agent 流程：

```text
输入：turn 证据 + memory index
  ↓
模型判断是否信息足够
  ↓
如不足，调用 read_topic_detail / read_memory_detail / expand_pointer
  ↓
模型输出 memory-changes-v1
  ↓
程序校验并写库
```

### 8.1 为什么使用 ReAct

直接一次性让模型输出最终 memory 有几个问题：

- 可能只看摘要就误判；
- 可能不知道已有 memory 正文；
- 可能重复 create；
- 可能无法判断是否冲突。

ReAct 让模型能：

```text
先查，再判断，再提交。
```

### 8.2 为什么模型不能直接写库

因为模型输出不可信，可能：

- 字段多/少；
- ID 编造；
- 引用错误 evidence；
- 误改 topic_key；
- 重复写入；
- 同一 turn 重跑污染数据。

所以采用：

```text
模型只输出计划；
本地代码做 schema 校验、引用校验、幂等校验、落库。
```

## 9. memory-changes-v1 计划格式

写入计划统一为：

```json
{
  "schema_version": "memory-changes-v1",
  "turn_id": "turn_xxx",
  "reason": "整体判断",
  "changes": []
}
```

当前支持 action：

```text
create_memory
update_memory
merge_memory
mark_conflict
update_topic
record_conflict_decision
noop
request_more_evidence
```

这种设计的好处：

1. 一个 turn 可以同时做多个动作；
2. 例如用户偏好反转时可同时：
   ```text
   update_memory
   update_topic
   record_conflict_decision
   ```
3. 本地校验器可以统一处理 schema、幂等和错误返回。

## 12. 当前架构选择的权衡

### 12.1 为什么先不做 LangGraph

当前没有先上 LangGraph 的原因：

1. 当前最重要是打通 MVP；
2. 核心难点在证据结构、写入校验、幂等和冲突，不在框架；
3. 手写编排更容易观察每一步输出；
4. 之后如果流程稳定，再迁移到 LangGraph 更安全。

后续适合引入 LangGraph 的场景：

```text
多节点状态机稳定；
需要 checkpoint；
需要 human-in-the-loop 审查；
需要失败后续跑；
需要并发任务调度。
```

### 12.2 为什么暂时不做完整版本链

完整版本链会带来：

- revision 表；
- 回滚；
- 冲突分支；
- 历史证据链；
- 更复杂的展示和召回策略。

当前阶段重点是：

```text
能从真实 CP 长流程里稳定沉淀有价值记忆。
```

所以当前采用轻量方案：

```text
当前 memory + metadata + conflict_records
```

### 12.3 为什么保留 Markdown

数据库适合机器读写，Markdown 适合人看。

当前演示需要能回答：

```text
到底沉淀了什么？
主题是什么？
memory 内容是否有用？
是否重复？
是否与用户偏好一致？
```

因此 Markdown 是审查层，不是主存储。

```text
一条 memory 混合多个语义时可拆分；
Markdown 导出后主题结构仍一致；
重复执行不产生重复 memory。
```

### 14.6 P5：长期运行压测

目标：

```text
验证 20+ turn 连续处理后不重复、不污染、不丢证据。
```

测试集建议：

```text
5 轮用户偏好
5 轮编译修复
5 轮运行现象
5 轮无长期价值/noop
若干冲突/纠正 turn
```

验收标准：

```text
memory/topic/conflict 数量增长符合预期；
同一批 turn 重跑后数量不增长；
没有重复 topic；
没有重复 conflict；
Markdown 导出稳定。
```

### 14.7 P6：评估是否迁移到 LangGraph

当前手写编排适合 MVP。

满足以下条件后再评估 LangGraph：

```text
节点稳定；
状态字段稳定；
工具集合稳定；
需要 checkpoint / resume / human-in-the-loop；
需要并发或任务队列。
```

可能的 LangGraph 节点：

```text
load_turn
build_evidence_pool
load_memory_index
react_decide
execute_read_tools
validate_plan
commit_plan
export_markdown
quality_report
```

验收标准：

```text
迁移后与当前手写链路结果一致；
失败可从 checkpoint 恢复；
工具返回和数据库写入仍保持幂等。
```
