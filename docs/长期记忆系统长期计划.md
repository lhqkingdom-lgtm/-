# 长期记忆系统长期计划

本文档作为 CodePulse Memory Lab 后续优化的长期计划。后续所有功能推进、评测和汇报，都优先围绕这份计划展开。

核心目标：

```text
先防止垃圾进记忆；
再让高价值闭环进记忆；
再让 CP 真正用记忆；
最后解决长期运行和并发问题。
```

---

## 阶段 1：收紧记忆类型和质量边界

目标：先保证不乱存，宁可少存，不要污染长期记忆。

核心改动：

### 1. 限制 memory_type

长期记忆类型先收敛为：

```text
user_preference
compile_failure_experience
runtime_failure_experience
none
```

含义：

- `user_preference`：用户长期协作习惯、明确长期偏好、跨任务重复偏好、关键纠正。
- `compile_failure_experience`：编译、链接、构建、烧录前失败经验。
- `runtime_failure_experience`：烧录后运行现象、上板失败、定位、修复、验证经验。
- `none`：不沉淀。

其他类型，例如：

```text
workflow
build_experience
engineering_failure_pattern
hardware_config
requirement_generation
```

都应归并到上述三类，或者判为 `none`。

### 2. 增加 verification_status

建议状态：

```text
candidate
verified
rejected
```

规则：

- 用户习惯：默认 `candidate`；跨任务/多次出现或用户明确长期要求后可为 `verified`。
- 编译失败经验：编译通过后可为 `verified`。
- 运行失败经验：用户烧板确认修好后才可为 `verified`；未确认只能为 `candidate`。
- 用户说没修好：不能写成成功经验，可标记为 `rejected` 或记录为无效尝试。
- 无价值信息：`none`，不写 memory。

### 3. 收紧提示词

提示词必须明确：

- 当前项目参数不存。
- 单次任务边界不存。
- 未验证猜测不写 verified。
- 用户偏好必须长期、重复、明确，或者属于关键纠错。
- 编译经验必须有编译验证。
- 运行经验必须区分 candidate / verified。

### 4. 收紧评测集和质量报告

评测集按以下字段标注：

```text
expected_memory_type
expected_status
expected_scope
allowed_actions
forbidden_actions
should_not_extract
semantic_expectation
```

质量报告按类型检查：

- `user_preference`：是否长期/重复/明确纠正。
- `compile_failure_experience`：是否有错误、根因、修复、编译验证。
- `runtime_failure_experience`：是否有现象、根因、修复、用户确认/运行验证。
- `none`：是否真的没有写 memory。

达标标准：

- 一次性任务边界 case 不再 create。
- 当前项目 IO、阈值、路径不进 memory 主体。
- memory_type 不再发散。
- create 数量下降，但高价值工程经验不丢。
- 禁止信息泄漏率下降。
- 动作命中率保持或提升。

重点要防止沉淀：

- “这次只改某模块，别动其他功能。”
- “这次先别生成代码。”
- “这次改成 3 分钟方便测试。”
- 当前项目 IO 映射、阈值、路径、完整参数表。
- 未验证猜测。

允许沉淀：

- 用户明确长期偏好或多次重复偏好。
- 已验证编译失败经验。
- 已验证运行失败经验。
- 关键纠错，例如“项目代号不是芯片型号，芯片必须从工程配置确认”。

## 阶段 2：多 turn episode 闭环

目标：让系统能沉淀真正有价值的“烧录后问题修好了”的工程经验。

目标流程：

```text
用户反馈现象
  ↓
模型定位
  ↓
模型修复/编译
  ↓
用户烧板确认
  ↓
聚合成 verified runtime_failure_experience
```

需要能力：

1. 识别用户确认状态

需要识别：

- 好了
- 可以了
- 修好了
- 还是不行
- 部分好了
- 烧录后仍然没反应

2. 回看同 session 最近 N 个 turn

回看范围优先基于：

- 同 session
- 当前 turn 之前
- 最近 5～10 个 turn
- 时间接近

3. 通过 pointer 回查原始证据

pointer 用于取回：

- 用户原始现象
- 助手定位过程
- 代码修改说明
- 编译结果
- 用户确认反馈

4. 聚合 episode 证据链

理想结构：

```json
{
  "episode_id": "...",
  "status": "verified",
  "turns": [
    {
      "role": "symptom",
      "turn_id": "...",
      "evidence_refs": []
    },
    {
      "role": "diagnosis",
      "turn_id": "...",
      "evidence_refs": []
    },
    {
      "role": "fix",
      "turn_id": "...",
      "evidence_refs": []
    },
    {
      "role": "verification",
      "turn_id": "...",
      "evidence_refs": []
    }
  ]
}
```

5. 生成 verified / candidate / rejected 记忆

规则：

- 未确认前不写 verified runtime 经验。
- 用户确认修好后生成完整闭环记忆。
- 用户说没修好时不生成成功经验。
- 部分修好时只沉淀已确认有效的部分。

达标标准：

- 未确认前不写 verified runtime 经验。
- 用户确认修好后能生成完整闭环记忆。
- 用户说没修好时不生成成功经验。
- 能在报告里看到 episode 证据链。
- episode 评测覆盖：
  - 修好了
  - 没修好
  - 部分修好

## 阶段 3：召回使用

目标：让 CP 真正用上这些记忆。

核心能力：

- 需求阶段召回用户偏好。
- 编译失败时召回 `compile_failure_experience`。
- 烧录反馈时召回 `runtime_failure_experience`。
- 生成代码前避免踩已知坑。

建议召回策略：

```text
需求/对齐阶段：
  user_preference

编译/构建失败阶段：
  user_preference + compile_failure_experience

烧录后运行反馈阶段：
  user_preference + runtime_failure_experience

生成代码阶段：
  user_preference + 少量高置信工程经验
```

达标标准：

- CP 在新任务中能看到相关记忆。
- 召回内容不混入无关项目参数。
- 召回能减少重复问答或错误判断。
- 可以通过对照测试证明：
  - 无记忆时会问/会错。
  - 有记忆时能更快定位或少问。

## 阶段 4：长期稳定性与并发

目标：能长期跑，不把不同窗口、不同用户、不同项目的记忆搞混。

核心能力：

- 用户 ID 隔离。
- session/project 隔离。
- 多窗口轮询防并发写冲突。
- 冲突记忆处理。
- 定期整理、合并、压缩记忆。
- 可视化评测报告。

达标标准：

- 多窗口同时使用不串记忆。
- 同用户不同项目不会错误污染。
- 记忆可合并、可废弃、可追溯。
- 长期运行后记忆数量不会无限膨胀。
- 能用报告展示每次优化前后变化。

## 客观判断

这个系统能沉淀出对 CP 有帮助的记忆，但前提是不要追求“所有对话都抽一点”。

真正有价值的是少数高质量记忆：

- 稳定用户协作偏好。
- 已验证编译失败经验。
- 已验证烧录/运行失败闭环经验。

如果没有阶段 1 的质量边界，长期记忆会被项目参数和一次性任务污染。

如果没有阶段 2 的 episode 闭环，最有价值的“用户烧板确认修好了”的工程经验会被拆散，甚至提前写成未验证结论。

因此后续必须按本计划推进。
