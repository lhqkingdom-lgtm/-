# 长期记忆评测集重审标准（阶段 1.2 固化版）

本文档用于约束 `memory_eval_v1` 后续修改，避免按单次运行结果反复“对答案”。评测集的修改必须先符合这里的设计理念，再调整 case 期望。

## 1. 总目标

长期记忆只评估三类可复用信息：

1. 用户协作习惯：以后和这个用户/这类任务协作时，能减少重复问答、误操作或返工。
2. 编译/构建/烧录失败经验：以后遇到类似工具链、工程结构、编译/链接/烧录问题时，能更快定位和修复。
3. 板上运行现象定位经验：用户反馈现象后，已经定位到代码/硬件配置层原因，并有解决方向或验证结论。

长期记忆不用于保存当前项目需求文档、IO 表、阈值、路径、文件清单、完整日志、完整报告、临时测试参数。

## 2. 单 turn 与多 turn 的职责边界

### 2.1 单 turn 隔离评测只测“本轮是否值得写入”

`single-isolated` 每条 case 都应该视为一个全新用户记忆空间。因此：

- 可以期望：`noop`、`create_memory`。
- 可以宽松允许：`update_memory` / `merge_memory`，但不能把它们作为唯一正确动作。
- 不应该出现：只允许 `update_memory` / `merge_memory` 的单 turn case。

原因：单 turn 隔离模式没有历史记忆，强制要求 update/merge 不符合真实执行条件。

### 2.2 多 turn scenario 才测“合并、更新、补验证、去重”

以下能力必须放在 `scenario-sequential`：

- 第二轮反馈更新第一轮记忆。
- 用户确认修复后补充验证状态。
- 同类运行问题合并成一条更完整经验。
- 相似用户偏好跨项目合并。
- 主题摘要随记忆变化更新。

## 3. 三类记忆的写入门槛

### 3.1 用户协作习惯

可以沉淀：

- 用户明确表达长期偏好，例如“以后都……”“以后不要……”“我希望你先……再……”。
- 跨多轮重复出现的稳定协作方式。
- 明确纠正会影响未来行为，例如“不要瞎猜，不清楚就问”“关键版本先 git 保存方便回滚”。

不应沉淀：

- 单次任务边界，例如“这次只改 A，不要动 B”。
- 单次交付格式，例如“这次报告写中文/表格”。
- 当前项目路径、文件、版本名、一次性命令。

边界：如果单次表达本身带有明显长期语义，可写；否则单 turn 应 noop，多 turn 中重复出现后再合并为偏好。

### 3.2 编译/构建/烧录失败经验

可以沉淀：

- 有明确失败症状：报错、链接失败、HEX 无法生成、烧录失败、工具链限制。
- 有明确原因或有效修复方向。
- 有编译/构建/烧录验证，或至少明确“待验证”。

不应沉淀：

- 纯“帮我编译/生成 HEX”的请求。
- 单次构建成功本身。
- 完整编译日志、路径、临时文件位置。
- 没有 root cause 的环境猜测。

### 3.3 板上运行现象定位经验

可以沉淀：

- 用户反馈真实运行现象，并且本轮或上下文中已经定位出原因。
- 原因能泛化到代码/硬件配置/状态机/驱动模式。
- 有解决方向、已修改方案、编译验证或用户板上确认。

不应沉淀：

- 只有现象、没有定位结论。
- 只有需求参数或 IO 表。
- 当前项目的孤立数值，例如某个 ADCHS=18、某个引脚=P3.1。
- 未验证猜测被写成“已解决”。

候选规则：如果已有“现象 + 代码层根因 + 修复方向 + 编译通过”，但还没有用户板上确认，可以写成候选经验，必须明确“待板上验证”。

## 4. 动作期望设计规则

### 4.1 allowed_actions 不应过窄

评测集的 `expected_action` / `allowed_actions` 应表达“合理动作集合”，不是唯一答案。

建议：

- 低价值 case：只允许 `noop`。
- 单 turn 有新价值：允许 `create_memory`，必要时也允许 `update_memory`，但不能只允许 `update_memory/merge_memory`。
- 多 turn 重复问题：scenario 期望应检查最终是否发生过 `update_memory` / `merge_memory` 或没有重复 stable_key。

### 4.2 forbidden_actions 只用于硬边界

只在以下情况使用 forbidden：

- 低价值/一次性/失败未闭环 case 禁止写 memory。
- 明确项目参数 case 禁止写 memory。
- 明确不能改主题的工具边界测试。

不要因为某次模型输出不理想，就临时加 forbidden。

## 5. 结果质量标准

一条 memory 合格至少满足：

- 有明确适用范围。
- 有可复用价值，不只是当前项目事实。
- 不泄漏当前项目路径/完整 IO/完整日志/孤立参数。
- 类型正确：用户偏好、编译失败经验、运行现象经验不要混写。
- 验证状态准确：未板上验证就不能写成已验证。

运行现象类推荐结构：

```text
适用范围：...
现象：...
触发条件：...
根因：...
解决/处理原则：...
验证状态：已验证 / 编译通过待板上确认 / 待验证
```

编译失败类推荐结构：

```text
适用范围：...
失败症状：...
触发条件：...
根因：...
有效修复：...
验证方式：...
```

用户偏好类推荐结构：

```text
适用范围：...
用户偏好：...
协作要求：...
价值：...
边界：...
```

## 6. 本轮评测集需要修正的方向

基于上述原则，优先修正以下设计问题：

1. 把只允许 `update_memory/merge_memory` 的单 turn case 移入或绑定到 scenario；单 turn 版本允许 `create_memory` 或改成只做语义质量观察。
2. 对“只有运行现象、没有根因”的 case，期望应改为 `noop` 或 `candidate`，不能要求完整长期经验。
3. 对“纯构建请求”的 case，保持 `noop`；如果 turn 内实际包含工具链失败根因，应把 case_type 改为 `build_toolchain_issue`，而不是继续叫 `build_request`。
4. 对“单次中文/表格/只改某模块”的表达，默认 noop；只有明确长期语义或 scenario 中重复出现，才作为用户偏好。
5. 评测报告中把单 turn 指标和 scenario 指标分开统计，不能用 single-isolated 的 mismatch 否定 update/merge 能力。

## 7. 不匹配问题的定位顺序

发现 case 不匹配时，不能先假定模型错误，也不能先修改提示词或金标。必须依次检查：

1. 原始 turn：用户、助手和工具实际说了什么，哪些内容只是评测者推断。
2. 模型输入：core/candidate/pointer 是否保留了决定动作所需的证据，是否发生截断或错误摘要。
3. 模型过程：模型读取了哪些证据、是否调用补证据工具、最终理由是否符合现有规则。
4. 程序执行：校验或提交层是否错误拒绝、放行或改写了模型动作。
5. 评测金标：expected_action、should_extract 和 semantic_expectation 是否被原始证据直接支持。

完成上述检查后，才能把问题归类为：模型判断错误、证据包缺失、工具/程序错误、评测金标错误或指标误报。每次汇报必须说明定位证据和根因，不能只报告“动作不匹配”。
