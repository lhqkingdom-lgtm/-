# 从 0 到 CodePulse 长期记忆系统建设复盘

这份文档不是单纯的功能说明，而是对整个 Memory Lab 项目从想法出现、方案取舍、架构演进、踩坑修正到评测体系形成的复盘。重点回答几个问题：

- 为什么要做长期记忆；
- 为什么不是简单把聊天记录总结成 Markdown；
- 为什么最后选择“三层证据池 + ReAct 记忆 Agent + 数据库 + 评测集”；
- 如何让记忆长期运行后不垮、不乱、不互相矛盾；
- 如何证明沉淀出来的记忆真的有用，而不是鸡肋。

## 1. 最初为什么要做这个系统

最初的问题来自真实 CP 使用过程：一个嵌入式项目往往不是一次问答就结束，而是会经历需求对齐、生成代码、编译、烧录、用户反馈现象、再次定位、再次修复、最后复盘。

在这种长流程里，用户会反复表达很多有长期价值的信息：

- 用户希望 CP 怎么协作；
- 生成代码前应该确认哪些东西；
- Keil C51 编译失败一般怎么定位；
- 烧录后某些现象背后常见根因是什么；
- 哪些坑已经踩过，下次不要再踩。

但如果这些信息只留在一次会话上下文里，会出现几个问题：

1. 新窗口或新项目里模型忘记之前的教训；
2. 同类问题下次又重新问、重新猜、重新犯错；
3. 用户明明纠正过一次，后续 CP 还是重复错误；
4. 编译和烧录过程中形成的经验没有变成可复用资产；
5. 展示或复盘时只能翻聊天记录，很难说明“系统到底学到了什么”。

所以项目的核心目的不是“保存聊天记录”，而是把真实交互中产生的经验转成长期可用的结构化记忆，让未来相似任务少问、少错、少返工。

一句话目标：

> 需求文档存“当前项目最终要做什么”；长期记忆存“以后类似任务怎么少错、少问、少返工”。

## 2. 一开始考虑过哪些方案

### 2.1 方案一：直接总结整段会话

最直观的方式是把 CP 对话整段丢给大模型，让它总结成 `MEMORY.md`。

优点：

- 实现最快；
- 演示容易；
- 不需要复杂数据结构。

但很快暴露问题：

- 会话很长，token 成本高；
- 容易把当前项目参数写进长期记忆；
- 编译日志、文件路径、IO 表、阈值等噪声太多；
- 模型很难区分“需求文档内容”和“长期经验”；
- 以后要追溯为什么这么写，找不到证据来源。

这个方案适合 demo，不适合长期运行。

### 2.2 方案二：按主题维护 Markdown 文件

后来尝试把记忆落成主 `MEMORY.md` 和多个主题 Markdown 文件，比如用户偏好、编译经验、运行现象经验。

优点：

- 直观；
- 便于展示；
- 用户能直接看到沉淀了什么。

问题也很明显：

- Markdown 适合展示，不适合做增量维护；
- 合并、拆分、冲突处理很难稳定；
- 多轮更新时容易重复、覆盖或越写越长；
- 缺少结构化字段，不方便做评测；
- 主题摘要和主题正文之间容易漂移。

最后形成的判断是：Markdown 应该作为导出展示层，而不是唯一存储层。

### 2.3 方案三：规则硬切阶段 + 固定抽取

曾经也考虑过按阶段硬分类：

- 需求对齐阶段抽用户习惯；
- 编译阶段抽编译经验；
- 运行反馈阶段抽现象根因；
- 修复阶段抽解决方案。

这个方向有价值，但如果做成硬规则，会有风险：

- 阶段识别可能误判；
- 一个 turn 里可能同时包含需求、编译、运行反馈；
- 真实 CP 会话不总是按理想流程走；
- 粗筛太严可能把有价值信息提前丢掉。

所以后来没有把阶段识别作为硬路由，而是作为“软提示”：告诉大模型本轮大概率是什么阶段、建议关注什么，但最终是否沉淀仍由证据和长期价值标准决定。

### 2.4 方案四：LangChain / LangGraph

也讨论过用 LangChain 或 LangGraph 做编排。

它们的优点是：

- 流程图清晰；
- 工具调用、状态流转有框架支持；
- 后续复杂 Agent 编排更规范。

但当时项目还在探索核心链路，最关键的问题不是框架，而是：

- 什么该存；
- 怎么存；
- 模型怎么判断证据够不够；
- 写入怎么防止幻觉；
- 怎么评测记忆质量。

因此当时选择先手动搭建最小闭环。这样能更快暴露真实问题，避免一开始被框架复杂度拖慢。

当前判断是：等核心链路稳定后，可以再评估是否迁移到 LangGraph。

## 3. 最终选择的核心架构

当前架构逐步收敛为：

```text
CP SQLite 原始会话
        ↓
按 turn 切分
        ↓
生成三层证据池 core / candidate / pointer
        ↓
读取已有 memory/topic 索引
        ↓
ReAct 记忆 Agent 判断是否需要补证据
        ↓
调用只读工具补证据
        ↓
输出 memory-changes-v1 变更计划
        ↓
程序校验 schema / ID / 权限 / 类型 / 幂等
        ↓
写入 PostgreSQL
        ↓
导出 Markdown / 生成评测报告
```

这个架构的关键思想是：

- 原始对话不直接变成记忆；
- 先变成证据；
- 模型只能基于证据提出计划；
- 写库必须经过程序校验；
- 结果必须能被评测和回放。

## 4. 为什么设计三层证据池

三层证据池是整个项目里最关键的设计之一。

### 4.1 core

`core` 存本轮最关键的信息，例如：

- 用户明确反馈的现象；
- 用户明确纠正；
- 助手最终定位的根因；
- 编译/烧录/运行验证结论。

它的作用是让模型快速看到“这轮到底发生了什么”。

### 4.2 candidate

`candidate` 存可能有价值的信息，例如：

- 工具读取文件摘要；
- 编译摘要；
- 代码修改摘要；
- 过程性上下文。

它不一定都进入长期记忆，但可以帮助模型判断是否有长期价值。

### 4.3 pointer

`pointer` 不直接塞完整原文，而是保存可以回查原始信息的位置。

这样做有几个好处：

- 平时上下文不爆炸；
- 模型需要时可以通过工具补证据；
- 详细日志、完整 diff、完整对话不会污染 memory；
- 评测时可以追溯某条记忆来自哪里。

这套设计解决了一个核心矛盾：

> 不能把所有原文都给模型，否则成本和噪声太大；但也不能粗筛太狠，否则有用证据会被裁掉。

所以最终采用：

```text
core 给主线
candidate 给判断
pointer 给回查
```

## 5. 记忆到底存什么

项目最后收敛成三类主要长期记忆。

### 5.1 用户交互习惯 / 协作偏好

存的是用户长期希望 CP 怎么工作，而不是当前一次任务的临时要求。

应该存：

- 用户明确说“以后都这样”；
- 用户多次重复表达同类偏好；
- 用户明确纠正过 CP 的工作方式；
- 对未来协作有复用价值的流程要求。

不应该存：

- “本次只改这个模块”；
- “这次先不要动其他功能”；
- “把这次报告转成 Excel”；
- 某一次的临时展示要求。

这个边界是后来反复调整出来的。早期模型容易把“单次任务边界”误当成“长期用户偏好”，这是质量问题之一。

### 5.2 编译失败 / 修复经验

存的是编译、链接、烧录失败背后的可复用经验。

应该包含：

- 症状；
- 触发条件；
- 根因；
- 有效修复方式；
- 验证方式。

典型例子：

- Keil C51 不支持某些现代 C 写法；
- C51 中断函数重复定义导致编译失败；
- Keil 评估版或链接器配置导致程序大小/FLASH 容量问题；
- 多个 `.uvproj` 干扰云编译项目识别。

不应该存：

- 完整编译日志；
- 当前项目输出路径；
- 一次性生成 HEX 的请求；
- 只说明“编译通过”但没有失败修复上下文的记录。

### 5.3 用户反馈运行现象 → 根因 → 解决方法

这是嵌入式场景最有价值的一类。

应该存：

- 用户烧录后看到的现象；
- 助手或工具定位出的代码/配置根因；
- 修复方法；
- 编译验证；
- 如果有用户复测确认，要标为已验证。

典型例子：

- ADC 通道选择位宽不足导致选错通道；
- 硬件输入桩函数固定返回值导致主流程跑通但状态机不动；
- 自动感应逻辑覆盖用户手动关灯；
- LED 低电平点亮理解错误导致指示灯状态反向；
- RTC 实际频率与假设不同导致倒计时加速。

重要边界：

- 编译通过只能证明代码能编译；
- 不能证明板上现象已经修好；
- 如果没有用户复测，只能写“待板上验证”。

这个边界后来也专门加进了提示词。

## 6. 存储形式为什么从 Markdown 转向 PostgreSQL

一开始希望直接生成 `MEMORY.md` 和主题文件，因为展示直观。

但做到合并、更新、冲突、回查之后发现，Markdown 不适合当主存储。

最终选择 PostgreSQL 作为主存储，原因是：

- 可以给每条 memory 分配稳定 ID；
- 可以按 user_id 隔离不同用户；
- 可以存 topic、memory、evidence、conflict；
- 可以做幂等写入；
- 可以做查询、召回、评测；
- 后续支持多窗口和并发控制更自然。

Markdown 仍保留，但定位变成：

> 数据库存事实和结构，Markdown 做展示和汇报。

当前核心表设计包括：

- `users`：用户维度；
- `turns`：CP turn；
- `evidence_items`：三层证据；
- `memory_topics`：主题摘要；
- `memories`：具体记忆；
- `memory_revisions`：记忆版本；
- `memory_conflict_records`：冲突记录；
- `memory_relations`：合并、替代、冲突等关系。

## 7. 为什么引入 ReAct 记忆 Agent

早期是一轮证据直接让模型输出最终记忆。

问题是：

- 模型可能没看到足够上下文；
- 它可能只凭摘要就更新旧记忆；
- 它可能不知道已有记忆里有没有重复；
- 它可能不知道主题是否需要调整；
- 它无法解释为什么不补证据。

所以后来改成 ReAct 流程。

模型先看到：

- 当前 turn 的三层证据池；
- topic_index；
- memory_index；
- 当前允许工具。

如果信息不够，它可以请求只读工具：

- 搜索相关记忆；
- 读取 memory 详情；
- 读取 topic 详情；
- 查看 memory 历史；
- 查看冲突记录；
- 回查 pointer 原文；
- 查看关系链。

只有证据足够后，才输出最终 `memory-changes-v1`。

关键安全边界是：

> 模型不能直接写数据库，只能输出计划；程序负责校验和提交。

## 8. 工具设计是怎么定下来的

工具设计参考了几个原则：

1. 职责单一；
2. 输入 schema 强约束；
3. 输出能继续推理；
4. 错误要能恢复；
5. 幂等；
6. 可审计；
7. 不越权。

### 8.1 读工具

读工具主要给模型补证据：

- `search_related_memories`：搜索可能相关的旧记忆；
- `read_memory_detail`：读取记忆正文；
- `read_topic_detail`：读取主题详情；
- `list_topic_memories`：列出主题下记忆；
- `read_memory_history`：查看版本历史；
- `list_memory_conflicts`：查看冲突记录；
- `trace_memory_relations`：查看关系链；
- `expand_pointer`：回查原始证据。

### 8.2 写动作

写入不是直接给模型一个“写数据库工具”，而是让它输出变更计划：

- `create_memory`
- `update_memory`
- `merge_memory`
- `merge_existing_memories`
- `retire_memory`
- `move_memory_topic`
- `update_topic`
- `merge_topics`
- `mark_conflict`
- `record_conflict_decision`
- `record_memory_relation`
- `noop`

后续统一由程序校验：

- action 是否合法；
- ID 是否存在；
- evidence 是否属于当前 turn；
- memory_type 是否允许；
- 是否读取过目标 memory；
- 是否越权修改 topic；
- 是否重复写入；
- 是否需要处理冲突。

这样既给了模型足够自由度，又避免它直接破坏数据库。

## 9. 走过的主要歪路

### 9.1 抽取规则一开始太严

一开始为了避免污染记忆，规则设得很严。

结果是：

- 很多候选经验被 noop；
- 需要展示时沉淀不够明显；
- 用户真实反馈现象还没形成闭环就被丢掉。

后来调整为：

- 核心链路先打通；
- 不要一开始把规则做死；
- 允许候选经验存在，但要标注验证状态；
- 后续用评测不断收紧质量。

### 9.2 又一度太宽，什么都想存

后来又出现相反问题：模型把很多当前项目参数、路径、一次性任务边界都存进去。

例如：

- 定时改成 3 分钟；
- 本次只改某个模块；
- 代码输出路径；
- 当前 IO 映射表。

这些不应该进入长期记忆。

后来逐渐收紧为三类 memory_type：

- `user_preference`
- `compile_failure_experience`
- `runtime_failure_experience`

并明确：

- 没有这三类长期价值就 noop；
- 不允许模型发明 `workflow`、`runtime_failure_pattern`、`build_experience` 等散乱类型；
- 单次任务边界不直接升级为长期用户偏好。

真实例子：

- 用户说“将定时功能改到三分钟，方便我测试时间压缩，其他先不要改变”。这句话一开始很容易被误判成“用户偏好只改指定内容”。后来重新判断后认为它只是本次测试参数和任务边界，不应该长期沉淀。
- 用户说“本次修改只改雷达感应部分，不改动其他功能”。最初评测集把它标成 user_preference，后来审计认为它是单次任务边界，除非未来反复出现或用户明确说“以后都这样”，否则应该 noop。

### 9.3 阶段识别被高估

一开始很关注“这是需求阶段、编译阶段还是运行阶段”。

后来发现，真实 turn 经常混合多个阶段。

比如用户开头只是给需求，助手最终可能完成代码、编译、修复多个错误；如果只按开头阶段处理，就会漏掉后面的编译经验。

所以最后阶段识别只做软路由：

- 提醒模型本轮大概率侧重点；
- 但不决定最终能存什么；
- 最终仍以证据和长期价值判断。

真实例子：

- 有些 turn 开头是用户给需求书和 IO 文件，看起来像“需求生成阶段”，但同一轮助手后面完成了代码生成、编译、修复多个错误。如果只按开头阶段处理，就会漏掉后面的编译经验。
- 有些 turn 被规则初判成 `compilation`，但实际里面包含用户偏好、项目需求和工具链问题。所以后面明确：阶段标签只能作为侧重点，不能作为硬裁剪依据。

### 9.4 评测集一开始也不够稳

评测不是一开始就完善的。

早期只看“有没有输出 memory”，后来发现这不够。

一个结果可能：

- 动作对了，但类型错了；
- 类型对了，但把项目参数写进长期记忆；
- 记忆有内容，但没有证据；
- 有证据，但没有说明验证状态；
- 没有重复 stable_key，但语义拆得太碎。

所以评测集后来增加了很多字段：

- `expected_action`
- `allowed_actions`
- `forbidden_actions`
- `expected_memory_type`
- `expected_status`
- `expected_scope`
- `should_extract`
- `should_not_extract`
- `expected_evidence`
- `expected_process`
- `semantic_expectation`

最近也发现评测集本身需要逐条审计，不能边跑边随手改。现在已经生成了逐条核对报告。

真实例子：

- 在阶段 1.2 测试时，我直接把 `single_preference_002` 从 user_preference 改成 noop。用户提醒“不要乱改评测集，要先一条一条核对”。这个提醒非常关键，因为评测集是基准，如果边测边随手改，后续优化指标就不可信。
- 随后补了两份审计报告：`memory_eval_v1_case_audit.md` 和 `memory_eval_v1_case_audit_reviewed.md`，先把 40 条 case 全部核对，再决定哪些要统一调整。

## 9.5 真实交互推进时间线

下面这部分按真实交互过程总结，而不是抽象设计。

### 9.5.1 从 CP 需求对齐问答开始

一开始的测试不是直接写代码，而是先观察 CP 在真实嵌入式项目里怎么提问。

当时 CP 会连续问：

- 失效进入条件：连续几次采样异常才认为传感器失效；
- ADC 来源：SoC 片内 ADC 还是外挂 ADC；
- 定时器分配：PWM 和采样周期分别用哪个 timer；
- NTC 参数、ADC 通道、PWM 通道、风扇类型、温区设计等。

这些问题让我们意识到：

1. CP 会在需求阶段产生很多当前项目参数；
2. 这些参数应该进需求文档，不应该进长期记忆；
3. 真正应该长期沉淀的是“以后类似风扇温控项目要确认哪些硬件资源和安全策略”。

这也是后来形成那句规则的来源：

> 需求文档存当前项目最终要做什么；长期记忆存以后 CP 怎么少问、少错、少返工。

### 9.5.2 为了下午展示，先放宽规则打通链路

当时用户有展示压力，明确说“硬性规则可以先不改，最重要打通沉淀好”“原本规则很严也可以取消”。

所以项目早期没有追求完美抽取，而是先验证：

- 能不能从真实 CP 会话里抓到 turn；
- 能不能生成主 memory 和主题文件；
- 能不能看到沉淀内容；
- 能不能让用户在 CP 里继续测试。

这个阶段的价值是快速把链路跑通，但也暴露出质量问题：

- 有些主题文件内容太少；
- 有些记忆过于泛；
- 有些当前项目内容被混进长期记忆；
- Markdown 可展示，但不适合长期维护。

### 9.5.3 “代码生成过程不抓，重点抓修复经验”的取舍

用户担心生成代码上下文太大，DeepSeek 或其他模型塞不进去，于是讨论过：

- 代码生成过程要不要抓；
- 一次编译通过怎么办；
- 编译失败后自动修复怎么沉淀；
- 用户烧板反馈现象后，怎么把原因和解决方案沉淀下来。

最后形成的取舍是：

- 代码生成过程本身不作为长期记忆重点；
- 如果一次编译通过，通常不沉淀，除非验证了某个已知失败修复；
- 编译失败时沉淀“症状 → 原因 → 修复 → 验证”；
- 用户烧板反馈现象后，沉淀“现象 → 代码层根因 → 解决方案 → 是否用户确认”。

这个取舍避免了把大量代码 diff、函数名、变量名都塞进长期记忆。

### 9.5.4 ADC 桩函数案例让“运行现象记忆”变具体

中间有一个非常典型的真实案例：风扇不转。

分析过程是：

```text
timer0_isr → sys_tick_flag = 1
main loop 调用 temp_sensor_read()
adc_sample() 永远返回 2048
adc_to_temp(2048) 得到 25℃
25℃ 低于风扇启动阈值
fan duty = 0
风扇不转
```

根因是 `adc_sample()` 只是桩函数，固定返回 2048，并没有读取真实 ADC 寄存器。

这个案例后来被抽象成更通用的规则：

> 硬件抽象桩函数直接返回固定常量，会让主流程完整跑通但输入数据恒定，导致下游状态机永远停在初始档位；编译通过只说明语法和链接正确，不代表硬件相关功能可用。

这个案例非常关键，因为它说明长期记忆不应该只存“MJ60B 风扇不转”，而应该存“硬件输入桩导致主流程假跑通”的可复用经验。

### 9.5.5 从 `MEMORY.md` 到 PostgreSQL

早期用户一直在看：

- 主 `MEMORY.md`；
- 主题 Markdown；
- “沉淀的新记忆去哪看”；
- “主题记忆文件咋啥也没有”。

这说明 Markdown 展示很重要。

但随着需求变复杂，用户又提出：

- 多个主题；
- 冲突；
- 合并；
- 拆分；
- 版本；
- 证据；
- 多窗口；
- 同事数据库；
- 评测。

这时 Markdown 的局限非常明显。后来用户提出“我想重构了，回去用 langgraph，然后记忆还有证据存数据库里一步步重新开始”。

最终没有立刻上 LangGraph，而是先用 PostgreSQL 打最小 MVP：

- 先建 memory/topic/evidence 表；
- 先把一个 turn 的三层证据入库；
- 先做工具；
- 再接 ReAct；
- 最后再考虑框架化。

这个顺序避免了还没搞清楚数据结构就先被框架绑住。

### 9.5.6 PostgreSQL 连接和表可见性问题

数据库阶段也踩过实际坑。

用户一开始用 DBeaver 连接 PostgreSQL，不知道怎么填：

- host；
- port；
- database；
- username；
- password。

后来又出现“怎么一个表没有”的问题，因为连接到了错误端口或默认 `postgres` 库。

过程中确认过：

- 有的环境是 5432；
- 有的测试服务是 55432；
- 后续评测用过 55512；
- 不能只看连接名，要确认 database 和 schema 下有没有表。

这个过程让系统后来更重视配置文件和连接参数记录，避免“表其实在另一个库里”这种低级但常见的问题。

### 9.5.7 轮询入口从手动脚本变成实时服务

后来用户希望真正接 CP，不想每次手动导出。

于是讨论了几种入口：

- CP 主流程主动发送；
- 轮询 CP SQLite；
- 多设备统一服务；
- 后续接召回。

为了先跑通，选择了最简单的轮询：

```text
CP 测试完成
      ↓
轮询检测新 turn
      ↓
处理三层证据池
      ↓
ReAct 记忆 Agent
      ↓
终端输出本轮处理结果
      ↓
详细 trace 写入 reports
```

真实测试中也遇到几个问题：

- 用户在 cmd 里直接换行运行 PowerShell 参数，导致参数被当成命令；
- 脚本里有 PowerShell 语法错误；
- 子进程输出编码报错；
- 一开始跑的是 dry-run，结果用户问“这算成功吗”；
- 轮询一直显示新 turn=0，后来发现可能没扫到当前会话；
- 后来改成终端中文日志，输出“第 N 轮扫描、新 turn、已完成、记忆动作”。

这些真实问题推动了轮询日志和 trace 文件设计。

### 9.5.8 可视化和日志的取舍

用户希望看到：

- 每次跟 CP 交互什么进去了；
- 分成几个 turn；
- 调用了什么工具；
- 最后记忆发生什么变化；
- 更详细内容能存成文件。

一开始想生成 HTML trace，但用户反馈信息太多、抓不住重点，还问“为什么调用 14 显示只有一个工具”。

后来形成更实用的方案：

- 终端输出简洁中文实时日志；
- 每轮详细交互写 JSON 文件；
- 后续再做 HTML/评测平台；
- 先保证真实长流程测试能跑。

这个取舍也体现了项目推进方式：

> 先让开发和调试链路可用，再做漂亮展示。

### 9.5.9 评测集不是一次定好的

评测集最初是为了回答一个问题：

> 现在沉淀出来的记忆到底有没有用？

一开始只是跑结果，后来用户追问：

- 什么叫有用；
- 指标是什么；
- 哪些能自动算；
- 哪些需要大模型或人工判断；
- 过程指标有没有；
- 评测集每条应该期待调用什么工具。

于是逐渐补出了：

- allowed_actions；
- forbidden_actions；
- expected_memory_type；
- expected_scope；
- should_extract；
- should_not_extract；
- expected_process；
- semantic_expectation。

最近又发现评测集本身可能有错，所以又生成了逐条审计报告。

这个过程说明评测集不是静态真理，而是需要像代码一样维护。

### 9.5.10 最近一次重要纠偏：不要乱改评测集

最近阶段 1.2 测试时，我看到 `single_preference_002` 更像一次性任务边界，就直接改成 noop。

用户马上指出：

> 你这不要乱改评测集啊，先把评测集重新一条一条核对好没问题。

这个纠偏非常重要。

因为如果一边优化提示词一边随手改评测集，最终指标变好可能只是因为基准被改了，而不代表系统真的变好了。

所以现在新的流程是：

1. 先生成逐条审计报告；
2. 标记通过、基本通过、需调整、待定；
3. 用户确认后统一修改评测集；
4. 再跑新的 baseline；
5. 再继续优化模型或工具。

这让评测链路更接近工程化流程。

### 9.5.11 真实轮询样例：哪些沉淀、哪些不沉淀

后面接入轮询后，系统开始从 CP SQLite 里自动扫描 turn。下面是几条真实跑出来的样例，能体现当时的判断方式。

| 真实 turn / 日志 | 输入特征 | 系统动作 | 为什么这样判断 |
| --- | --- | --- | --- |
| `turn_22ee3369...`，报告 `react-20260921T084916339195Z-c3c668aabdd7.json` | MJ60B 温控风扇项目需求对齐，包含已有 Keil C51 工程、不要重建工程、不要改 `STARTUP.A51`、优先沿用现有驱动，也包含大量阈值、IO、PWM 参数 | `create_memory=2` | 阈值、IO、PWM 频率属于当前项目需求，不进长期记忆；但“不重建工程、不改 STARTUP.A51、基于已有工程二次开发”属于可复用用户协作/工程流程偏好 |
| `turn_d998317...`，报告 `react-20260921T084922862768Z-b2b32299c621.json` | 读取 `miji_config.h`、`miji_porting.h` 后发现当前工程仅风扇温控启用、很多引脚为占位符 | `noop` | 这是当前工程配置状态，可从代码恢复；不是用户偏好，也不是编译/运行失败经验 |
| `turn_f562728...`，报告 `react-20260921T085933644854Z-bf6a2ae74619.json` | 用户给出 NTC 规格、采样周期、PWM 频率、温度阈值、传感器失效策略，并要求先整理需求文档 | `noop` | 这些是本项目需求参数，应进需求文档；“先整理需求文档”在当时只是本轮任务指令，还不能直接升级为长期偏好 |
| `react-20260921T065955032593Z-304d2071d573.json` | 用户反馈风扇在 36℃ 阈值附近频繁启停，并要求先从代码排查 | `noop` 或补证据倾向 | 已有记忆已覆盖“阈值附近频繁启停通常要检查滞回/滤波”和“运行异常优先查代码”；本轮没有新的根因、修复和用户确认，所以不重复新增 |

这些例子也暴露出两个真实问题：

1. 早期真实输出里出现过 `memory_type=workflow`，说明模型会自己发明类型。后来才把类型收紧为 `user_preference`、`compile_failure_experience`、`runtime_failure_experience` 三类。
2. 很多 turn 看起来信息很多，但真正有长期价值的很少。比如一整轮需求对齐可能有几十条参数，但长期记忆只应该抽出一两条“以后能少问、少错、少返工”的规则。

所以后来的优化目标不是“沉淀得越多越好”，而是：

- 当前项目参数不进长期记忆；
- 可从代码、需求文档、Git 恢复的信息不进长期记忆；
- 只有能影响以后协作、编译修复、烧板现象定位的信息才进长期记忆；
- 如果已有记忆已经覆盖，就更新或补证据，不重复新增。

## 10. 矛盾处理方案是怎么考虑的

矛盾处理讨论过很多方案。

### 10.1 最复杂方案：完整版本链 + 冲突图

一开始考虑做得很完整：

- 每条 memory 都有版本；
- 每次修改都生成 revision；
- 记忆之间有 supersedes / merges / conflicts_with；
- 冲突记录单独存；
- 主题也有合并和迁移。

优点：

- 可追溯；
- 适合长期运行；
- 冲突不会被静默覆盖。

问题：

- 实现复杂；
- 工具数量变多；
- 评测成本高；
- 演示阶段容易被结构拖慢。

### 10.2 最简单方案：直接覆盖旧记忆

也考虑过“新记忆直接覆盖旧记忆”。

优点：

- 简单；
- 容易实现；
- 不需要维护冲突记录。

但这个方案风险很高：

- 不知道为什么覆盖；
- 老证据丢失；
- 用户前后偏好变化无法解释；
- 多项目条件差异容易被误当冲突。

最终没有采用。

### 10.3 当前折中方案：轻量版本链 + 冲突记录

当前选择的是中间方案：

- memory 当前态保存在 `memories`；
- 修改时写 `memory_revisions`；
- 冲突判断写入 `memory_conflict_records`；
- 合并/替代关系写入 relation；
- 不做过重的全量冲突推理；
- 先让模型通过工具查看历史和证据，再决定更新、合并、冲突或 noop。

当前冲突处理原则：

1. 不轻易把不同项目/芯片/工具链差异当成冲突；
2. 同一用户、同一范围、同一语义槽位前后相反才是冲突；
3. 能拆条件就拆条件；
4. 不能解释才标冲突；
5. 用户明确纠正时，记录旧说法、新说法、采用新说法的原因；
6. 合并或退役 memory 时，要考虑挂在旧 memory 上的冲突如何处理。

这个设计的目标不是一开始就解决所有冲突，而是保证：

> 未来发现冲突时，有工具、有字段、有流程可以承接，不会只能靠覆盖或遗忘。

## 11. 如何避免长期运行后记忆垮掉

长期记忆系统真正难点不是“写入一条记忆”，而是长期运行后不变成垃圾堆。

当前设计从几个层面控制。

### 11.1 类型收敛

只允许三类长期记忆：

- 用户偏好；
- 编译经验；
- 运行现象经验。

这样避免类型无限发散。

### 11.2 质量边界

新增沉淀前的三道门槛：

1. 长期价值门槛；
2. 类型必备证据门槛；
3. 当前项目参数过滤门槛。

如果只能回答“当前项目这次怎么做”，默认不存。

### 11.3 证据链

记忆不是凭空生成，而是要有 evidence_refs。

以后出现问题，可以回查：

- 是用户说的；
- 是助手推理的；
- 是工具结果；
- 是编译验证；
- 是用户复测确认。

### 11.4 写入校验

模型输出后，程序校验：

- schema；
- action；
- ID；
- evidence；
- memory_type；
- target 是否读过；
- topic 是否越权；
- 冲突状态；
- 幂等。

这样可以减少大模型幻觉对数据库的破坏。

### 11.5 评测闭环

每次提示词、工具、schema 改动后，都要通过：

- 单元测试；
- 小范围真实回放；
- 评测集指标；
- 人工审计报告。

这样不是凭感觉说“变好了”，而是有可比较的证据。

## 12. 评测链路是怎么设计的

评测链路经历了几次迭代。

### 12.1 最初只看结果

最早只看最终生成了什么 memory。

后来发现不够，因为模型可能：

- 碰巧输出对了；
- 没有查旧记忆；
- 没有证据引用；
- 记忆内容看起来不错但其实没有来源；
- 类型错了但语义差不多。

### 12.2 后来加入过程指标

现在评测既看过程，也看结果。

过程指标包括：

- 是否加载 memory_index；
- 是否存在 evidence package；
- 是否有 final reason；
- action 是否在 allowed_actions；
- 是否触发 forbidden_actions；
- 是否按需要补证据。

结果指标包括：

- expected action 是否匹配；
- memory_type 是否正确；
- should_extract 是否覆盖；
- should_not_extract 是否泄漏；
- 是否重复 stable_key；
- 是否过度拆分；
- 是否有症状、原因、解决、验证；
- 是否长期复用价值明确。

### 12.3 评测集怎么设计

评测集来自真实 CP 数据，而不是人工编造样例。

来源包括：

- 自己的 CP 测试会话；
- 同事的真实 CP SQLite；
- 嵌入式项目长流程；
- 编译失败；
- 烧录反馈；
- 多轮修复；
- 用户偏好表达；
- 低价值/noop 类输入。

每条 case 包含：

- `case_id`
- `case_type`
- `turn_id`
- `source_db`
- `expected_action`
- `allowed_actions`
- `forbidden_actions`
- `expected_memory_type`
- `expected_scope`
- `expected_status`
- `should_extract`
- `should_not_extract`
- `expected_process`
- `semantic_expectation`

最近新增了逐条核对报告，避免评测集本身成为不稳定来源。

当前已识别出一批需要核对的 case，例如：

- ADCHS 通道偏移不应归为编译失败，而更像运行/硬件配置经验；
- 单次“只改某模块”不应当成长期用户偏好；
- HEX 路径问题本身是 noop，但其中可能包含 Keil/云编译工具链经验；
- 失败 turn 如果没有助手结论，不应该强行沉淀。

这说明评测集本身也需要版本化和审计。

## 13. 当前已经实现的能力

目前已经打通的能力包括：

1. 从 CP SQLite 读取真实会话；
2. 按 turn 切分；
3. 生成三层证据池；
4. 入库到 PostgreSQL；
5. ReAct 记忆维护 Agent；
6. 只读工具补证据；
7. memory-changes-v1 写入计划；
8. 写入校验和 commit；
9. memory/topic 存储；
10. memory revision；
11. 轻量冲突记录；
12. 主题更新、主题合并、记忆移动；
13. Markdown 导出；
14. 轮询 CP 新 turn；
15. 终端实时日志；
16. 评测集回放；
17. 指标报告；
18. 逐条评测集审计。

## 14. 当前仍然没有完全解决的问题

### 14.1 拆分粒度

一轮 turn 可能包含多个运行问题。

有时拆成多条是合理的，因为根因完全不同；有时会显得过碎。

当前已有提示词要求：

- 同一根因多个表现合并；
- 不同根因可以拆；
- 超过 3 条要说明独立性。

但这仍需要继续评测。

### 14.2 多 turn episode 闭环

生成代码、用户烧录、反馈现象、修复、用户确认，这往往跨多个 turn。

目前系统主要还是按单 turn 处理。

后续需要 episode 级别聚合：

```text
现象出现
 → 定位根因
 → 修复
 → 编译通过
 → 用户板上确认
 → 标记 verified
```

### 14.3 召回使用还没完整验证

现在重点在“怎么沉淀”，还没系统验证“CP 如何在下一次任务中使用这些记忆”。

后续要做读链路：

- 根据当前任务召回相关 memory；
- 注入 CP 上下文；
- 观察是否减少问答、减少错误；
- 评测召回准确率和使用效果。

### 14.4 并发和多窗口

当前轮询更偏单机多窗口测试。

长期需要考虑：

- 一个 API key 多设备；
- 多窗口同时写；
- 同一用户不同项目；
- 写入锁；
- 幂等；
- 事务隔离；
- 冲突记录。

### 14.5 评测集仍需清洗

最近已经发现评测集里有部分 case 期望需要调整。

下一步应该先稳定评测集，再跑大规模对比，否则指标会被错误基准污染。

## 15. 项目最有含金量的部分

如果要对外讲这个项目，最有价值的点不是“用了大模型总结记忆”，而是下面这些：

### 15.1 把长期记忆当成工程系统，而不是提示词技巧

系统不是让模型随便总结，而是有：

- 数据来源；
- 证据池；
- 工具；
- schema；
- 校验；
- 版本；
- 冲突；
- 评测。

### 15.2 解决了真实长流程场景

评测数据来自真实 CP 嵌入式项目，不是玩具例子。

场景包括：

- Keil C51；
- ADC；
- PWM；
- 触摸按键；
- LED 极性；
- 雷达感应；
- RTC；
- 烧录反馈；
- 多轮修复。

这让系统设计更贴近真实复杂度。

### 15.3 明确区分需求文档和长期记忆

这是整个项目反复收敛出的核心原则。

需求文档：

- 当前项目要做什么；
- 阈值；
- IO；
- 功能选择；
- 参数。

长期记忆：

- 以后类似项目怎么做；
- 以前踩过什么坑；
- 用户长期怎么协作；
- 哪些错误如何定位和验证。

### 15.4 有评测闭环

不仅能生成记忆，还能评测：

- 是否该存；
- 存什么类型；
- 是否证据足够；
- 是否泄漏项目参数；
- 是否过度拆分；
- 是否动作合理；
- 是否可复用。

这比单纯 demo 更接近可持续迭代。

### 15.5 对冲突和长期维护有设计

虽然冲突处理还没完全成熟，但已经有思考和底座：

- 不直接覆盖；
- 保留 revision；
- 记录 conflict decision；
- 支持 merge / retire / relation；
- 支持后续回查证据时间线。

这保证系统未来可以继续演进，而不是越用越乱。

## 16. 可以怎么在简历或汇报里描述

可以这样概括：

> 我从真实 CodePulse 嵌入式开发会话出发，设计并实现了一套长期记忆沉淀系统。系统将原始 CP SQLite 会话按 turn 切分，构建 core / candidate / pointer 三层证据池，再由 ReAct 记忆 Agent 结合已有 memory/topic 索引和只读工具进行证据补全，最终输出结构化 memory-changes 计划。写入前由程序校验 schema、证据引用、目标 ID、memory_type、权限边界和幂等性，避免大模型直接写库带来的幻觉风险。系统将长期记忆收敛为用户协作偏好、编译失败经验、运行现象定位经验三类，并通过 PostgreSQL 存储 memory、topic、revision、conflict 与 relation。为了验证沉淀质量，我基于真实 CP 项目会话构建评测集，设计了过程指标和结果指标，包括证据覆盖、动作合理性、类型准确性、项目参数泄漏、过度拆分和长期复用价值等，用离线回放持续定位提示词、工具和数据集问题。

## 17. 当前推荐下一步

当前最应该做的不是继续盲目跑大规模评测，而是：

1. 先完成评测集逐条核对；
2. 统一修正评测集；
3. 重新跑一版稳定 baseline；
4. 再继续优化 1.3 拆分/合并粒度；
5. 然后进入 episode 多 turn 闭环；
6. 最后做召回使用和并发稳定性。

如果评测集本身不稳定，后面的指标对比就没有可信度。

## 18. 总结

这个项目从一开始的“能不能把 CP 会话总结成记忆”，逐步变成了一个更完整的问题：

> 如何从真实长流程 AI 编程交互中，可靠地提取、维护、评测和使用长期记忆。

现在的系统已经不是单纯的 prompt demo，而是一个有数据流、有工具、有数据库、有校验、有评测、有冲突处理规划的长期记忆实验平台。

它还没有完全完成，尤其是多 turn episode、召回使用、并发和评测集清洗仍需继续推进。但核心链路已经证明可行：真实 CP 会话可以被切成证据，证据可以驱动模型做结构化记忆维护，记忆可以被写入数据库并接受评测，后续可以围绕指标持续优化。
